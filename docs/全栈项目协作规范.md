# 全栈项目协作规范

## 目标与适用范围

本规范用于前后端分离、包含数据库并需要独立部署的项目。它与《[部门协作规范](部门协作规范.md)》并列使用：简单的单页网站继续使用原流程；出现独立前端、后端、数据库、登录权限或多环境部署时，切换到本规范。

本规范不绑定具体技术栈。React、Vue、Node、Java、MySQL、PostgreSQL 或其他替代方案都可以使用，但必须遵守接口、数据、安全和发布的交接规则。

## 角色与职责

角色是工作分工，不要求一直运行多个 Agent。项目经理根据当前阶段临时派遣角色，并以文档作为唯一交接依据。

| 角色 | 主要职责 | 必须产出 |
| --- | --- | --- |
| 项目经理 | 确定目标、范围、优先级、预算和最终验收 | 需求确认、阶段决策、验收结论 |
| 需求部门 | 描述用户、流程、范围、非范围和验收标准 | 需求说明、任务清单 |
| 架构部门 | 拆分前后端和基础设施，识别关键风险 | 系统架构、技术选型、架构决策记录 |
| API 设计部门 | 定义接口、数据格式、错误码和权限 | API 接口契约 |
| 数据库部门 | 设计表结构、索引、迁移、备份和回滚 | 数据库设计、迁移文件、数据字典 |
| 前端部门 | 实现页面、状态管理、接口调用和用户反馈 | 前端代码、页面测试记录 |
| 后端部门 | 实现业务规则、API、校验、权限和事务 | 后端代码、API 测试结果 |
| 测试部门 | 执行单元、接口、联调、回归和异常测试 | 测试报告、缺陷清单 |
| 安全部门 | 检查认证、授权、输入、密钥、依赖和数据保护 | 安全检查记录、整改项 |
| 发布运维部门 | 管理环境、CI/CD、发布、监控、备份和回滚 | 发布记录、运行手册、事故记录 |

## 项目阶段与质量门禁

每一阶段都要有明确的输入、产出和交接条件。未达到门禁时，下一阶段不得以“先做再说”的方式开始。

### 1. 需求确认

- 输入：项目目标、用户问题和业务约束。
- 产出：用户流程、功能范围、非范围、权限角色、验收标准和优先级。
- 交接条件：每项功能都有可观察的验收结果；项目经理确认第一版范围。
- 项目经理确认：做什么、不做什么、谁能使用、什么情况算完成。

### 2. 架构设计

- 输入：已确认的需求和非功能要求（性能、可用性、合规等）。
- 产出：前端、后端、数据库及第三方服务的边界；数据流；技术选型；关键架构决策记录。
- 交接条件：服务边界、调用方向、认证方式、失败处理和部署拓扑已说明。
- 项目经理确认：复杂度、成本、交付时间和主要风险可接受。

### 3. API 与数据库设计

- API 先于前后端实现确定。接口契约至少包含路径、方法、鉴权、请求参数、响应结构、错误码和版本。
- 数据库设计至少包含实体关系、字段类型、约束、索引、敏感字段、初始化数据和迁移策略。
- 产出：API 契约、数据库设计、数据字典和迁移方案，分别使用[接口契约模板](交接/API接口契约模板.md)与[数据库变更模板](交接/数据库变更模板.md)。
- 交接条件：前端、后端和数据库负责人共同评审；接口与数据模型没有未记录的假设。

### 4. 前后端并行开发

- 前端只依赖已确认的 API 契约，可使用约定好的模拟数据开发。
- 后端按契约实现业务规则、参数校验、权限检查、事务和统一错误响应。
- 数据库变更必须通过迁移文件提交，禁止只在本地手工改表后上线。
- 每项跨部门工作使用[全栈项目交接单](交接/全栈项目交接单模板.md)，记录影响范围和验证方式。
- 交接条件：代码可构建，单元测试或静态检查通过，变更记录完整。

### 5. 联调与测试

测试顺序建议为：单元测试 → API 测试 → 数据库读写测试 → 前后端联调 → 回归测试 → 安全检查。

- 覆盖成功、空数据、参数错误、未登录、无权限、超时、重复提交和服务异常。
- 检查数据库事务、并发写入、迁移兼容性和回滚可行性。
- 测试环境使用脱敏数据；测试账号、密钥和临时数据不得进入生产。
- 交接条件：阻断发布的缺陷已关闭；测试部门记录环境、版本、步骤和结果；项目经理确认验收。

### 6. 发布与上线

- 发布运维部门确认构建产物、迁移顺序、环境变量、备份点、监控和回滚命令。
- 生产发布采用可追踪版本（例如 Git 标签或发布号），并保留发布前后检查结果。
- 数据库迁移先验证向后兼容；需要破坏性变更时采用“新增字段 → 双写/回填 → 切换读取 → 清理旧字段”的分阶段方案。
- 上线后检查登录、核心业务、API 健康、数据库连接、日志和告警。
- 交接条件：发布记录包含版本、时间、执行人、网址、迁移结果和回滚点。

### 7. 监控、复盘与维护

- 记录应用错误、API 延迟和错误率、数据库连接/容量、任务队列（如有）及主机资源。
- 为影响核心业务的指标设置告警，并写明接收人、判断标准和处理步骤。
- 按项目要求执行数据库备份，定期验证备份能够恢复；备份本身也要限制访问。
- 事故处理遵循“止损 → 判断影响 → 回滚或修复 → 验证恢复 → 记录复盘”，不得直接删除证据或覆盖日志。

## 协作与交接规则

- 需求、架构、API、数据库和测试结论必须写入文档；聊天内容不能作为唯一依据。
- API 契约变更必须注明兼容性、版本和前后端切换顺序。未经评审，不得改变字段含义或错误码。
- 数据库迁移必须可审查、可重复执行或明确幂等，并提供回滚或恢复方案。
- 环境变量只提交名称和示例值；真实密钥放在平台密钥管理中，禁止提交到仓库、日志或截图。
- 一个任务同一时间只允许一个角色修改同一份文件；交接完成后由下一角色确认接收。
- Agent 完成任务后退出；后续问题重新派遣对应角色，避免多个 Agent 同时修改同一模块。
- 项目经理在开发前、联调前、发布前和上线后分别做范围、质量、风险和结果确认。

## 分支、评审与自动检查

- 一个功能一个分支或变更单，提交信息说明目的；禁止直接在生产分支堆积未经验证的修改。
- 合并前至少完成代码评审、构建、静态检查、自动化测试和必要的数据库迁移检查。
- CI 失败时停止合并和发布；修复后重新执行，不以手工“确认通过”替代自动检查。
- 发布使用已评审的提交或标签；紧急修复也必须补齐测试和变更记录。

## 环境与配置

| 环境 | 用途 | 数据要求 | 发布规则 |
| --- | --- | --- | --- |
| 开发 | 日常实现和本地调试 | 可使用构造或脱敏数据 | 允许频繁变更 |
| 测试 | 自动化测试和联调 | 必须可重置、不可使用真实敏感数据 | 由开发或 CI 发布 |
| 预发布 | 上线前的真实配置演练 | 结构接近生产，数据继续脱敏 | 项目经理批准后发布 |
| 生产 | 面向真实用户 | 真实数据，必须备份和审计 | 仅发布已验收版本 |

## 最小发布检查清单

- [ ] 需求、API、数据库和测试文档已更新。
- [ ] 构建、静态检查、自动化测试全部通过。
- [ ] 生产环境变量和密钥已配置，且未进入代码仓库。
- [ ] 数据库备份完成，迁移顺序和回滚方案已演练或验证。
- [ ] 发布版本、执行人、时间和目标环境已记录。
- [ ] 上线后核心流程、日志、监控和告警正常。
- [ ] 出现问题时能定位回滚点和负责人。
