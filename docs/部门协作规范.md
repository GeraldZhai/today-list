# 部门协作规范

## 目标

让每个功能都有清楚的负责人、交接材料和验收标准。角色名称是工作分工，不代表需要一直运行多个 Agent。

## 角色与职责

| 角色 | 谁担任 | 主要职责 | 主要产出 |
| --- | --- | --- | --- |
| 项目经理 | 你 | 确定优先级、确认范围、最终验收 | 决策与验收结论 |
| 需求部门 | 临时需求 Agent | 把想法写成用户流程、范围和验收标准 | `01-需求说明.md` |
| 产品设计部门 | 临时设计 Agent | 确定页面交互、数据字段和实现边界 | `02-技术方案.md` |
| 开发部门 | 临时开发 Agent 或主 Agent | 实现代码、处理数据兼容 | 代码与变更记录 |
| 测试部门 | 临时测试 Agent | 按验收标准测试，记录问题和结果 | `04-测试记录.md` |
| 发布运维部门 | 临时发布运维 Agent | 发布检查、部署、回滚、运行检查和故障记录 | `06-部署运维.md` |

## 一次功能迭代怎样流转

1. 项目经理提出功能，例如“给任务增加分类”。
2. 需求部门在任务清单中建立任务编号，补充范围、非范围和验收标准。
3. 项目经理确认需求；小功能可以直接在对话中确认。
4. 产品设计部门确定页面、数据字段和影响文件；有明显取舍时必须列出让项目经理决定。
5. 开发部门只按已确认方案修改代码，并更新变更记录。
6. 测试部门按验收标准实际操作，结果写入测试记录；发现问题则退回开发部门。
7. 项目经理查看测试结论，决定“验收通过”或“进入下一轮”。
8. 验收通过后，发布运维部门执行上线检查；涉及外部平台时先由项目经理选择平台并授权。
9. 上线后记录版本、网址和回滚点，并按运维清单检查可访问性与数据风险。

## 交接规则

- 每次跨部门交接都使用 `交接/功能交接单模板.md` 的字段。
- 交接单必须写清楚：本次完成什么、影响哪些文件、如何验证、是否有风险、下一位需要做什么。
- 需求部门不修改业务代码；测试部门不借测试名义顺手改功能。
- 发布运维部门不能擅自开通付费服务、上传代码或修改域名。
- 同一时间只允许一个角色修改同一份文件，避免相互覆盖。
- 子 Agent 完成后退出；下一次再根据任务内容重新派遣对应角色。

## 项目经理的三个确认点

1. 开发前：范围和验收标准是否正确。
2. 部署前：测试记录是否足以说明功能可用，并选择部署平台。
3. 发布后：线上网址是否正常，是否接受当前的数据保存与运维风险。

你不需要写技术细节。只需要用普通语言确认“做什么、不做什么、看起来是否符合预期”。
